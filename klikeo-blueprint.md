> Generated by The Architect on 2026-05-17
> Archetype: SaaS / Web App + Mobile App (Monorepo)

---

## 1. Project Overview

### Vision

Klikeo centraliza el comercio local en Colombia. Cada negocio obtiene un perfil público descubrible y un chatbot de WhatsApp personalizado, entrenado con los datos del propio negocio, que atiende clientes 24/7 sin intervención humana.

El producto resuelve dos problemas reales: los negocios locales no tienen presencia digital efectiva, y los clientes no pueden obtener información básica (horarios, precios, disponibilidad) fuera del horario laboral.

### Goals

- Registrar negocios con perfil público + chatbot de WhatsApp activado
- Permitir a cada dueño entrenar su chatbot con datos propios (menú, servicios, precios, políticas)
- Indexar negocios para que clientes los encuentren por categoría, ciudad o nombre

### Success Metrics

- 100 negocios registrados en el primer mes
- 50 chatbots activos atendiendo conversaciones en WhatsApp

## 4. Data Model

### Entities

**Negocio**
| Field | Type | Notes |
|-------|------|-------|
| _id | ObjectId | Auto-generado |
| name | string | requerido, min 2 chars |
| description | string | max 500 chars |

| phone | string | teléfono de contacto |
| whatsappNumber | string | número conectado a WhatsApp Business |
| logoUrl | string | URL de imagen en CDN/storage |
| ownerId | ObjectId | ref: Usuario |
| trainingData | string | datos para el prompt del chatbot |
| isActive | boolean | default: true |
| createdAt | Date | auto |

**Usuario**
| Field | Type | Notes |
|-------|------|-------|
| _id | ObjectId | Auto-generado |
| email | string | único, lowercase |
| passwordHash | string | bcrypt, nunca exponer |
| name | string | nombre del dueño |
| role | enum | 'admin' \| 'owner' |
| negocioId | ObjectId | ref: Negocio, nullable |
| refreshToken | string | hasheado en BD |
| createdAt | Date | auto |

**ChatSession**
| Field | Type | Notes |
|-------|------|-------|
| _id | ObjectId | Auto-generado |
| negocioId | ObjectId | ref: Negocio |
| clientePhone | string | número del cliente en WhatsApp |
| estado | enum | 'active' \| 'closed' |
| historial | Array | [{role, content, timestamp}] |
| createdAt | Date | auto |
| updatedAt | Date | auto al recibir mensaje |

**Message** (embebido en ChatSession.historial)
| Field | Type | Notes |
|-------|------|-------|
| role | enum | 'user' \| 'assistant' |
| content | string | texto del mensaje |
| timestamp | Date | cuándo se envió |

### Relationships

- Un **Usuario** (owner) posee un **Negocio** (1:1)
- Un **Negocio** tiene muchas **ChatSession** (1:N)
- Los mensajes se **embedden** en ChatSession.historial (no colección separada en MVP)

## 8. Authentication & Authorization

### Auth Flow

1. Dueño se registra → `POST /api/auth/register` → recibe `accessToken` en body + `refreshToken` en cookie httpOnly
2. Login → mismo patrón
3. Cliente Next.js almacena `accessToken` en memoria (no localStorage)
4. Middleware de Next.js lee cookie `refreshToken` para rutas `/dashboard/*`, `/mi-negocio/*`, `/chats/*`, `/chatbot/*`
5. Access token expira en 15min → API retorna 401 → cliente llama `/api/auth/refresh` automáticamente
6. Logout → `POST /api/auth/logout` → BD borra `refreshToken`, cliente limpia estado

### Protected Routes

- **Públicas**: `/`, `/negocios`, `/negocios/[id]`, `/login`, `/register`
- **Protegidas (owner)**: `/dashboard`, `/mi-negocio`, `/chats`, `/chatbot`
- El middleware de Next.js (`middleware.ts`) redirige a `/login` si no hay cookie válida

### Roles & Permissions

| Role | Puede hacer |
|------|-------------|
| owner | Crear/editar su negocio, ver sus chats, entrenar su chatbot |
| admin | Todo lo anterior + gestionar todos los negocios (panel admin, post-MVP) |

### Session Management

- `accessToken`: JWT firmado con `JWT_SECRET`, expiración 15min, payload: `{userId, role}`
- `refreshToken`: JWT firmado con `JWT_REFRESH_SECRET`, expiración 7 días, guardado hasheado en MongoDB
- Cookies: `httpOnly`, `secure` (producción), `sameSite: 'lax'`

## 16. Reglas No Negociables

1. **TypeScript estricto en todo el monorepo.** `strict: true` en todos los tsconfig. Cero `any` implícitos. Cero type assertions innecesarias.
2. **Cada endpoint tiene al menos un test de integración.** Sin excepción. Un endpoint sin test no se considera terminado.
3. **TDD obligatorio en la API.** El test se escribe antes de la implementación. Rojo → verde → refactor.
4. **La firma HMAC-SHA256 del webhook de WhatsApp se verifica en cada request entrante.** Un webhook sin firma válida retorna 403 inmediatamente.
5. **El chatbot siempre se identifica como asistente virtual del negocio.** Nunca como una persona real. El prompt del sistema lo enforcea.
6. **Un componente/use case/controller por archivo.** Máximo 200 líneas. Si excede, extraer.
7. **Nunca commitear `.env`.** Solo `.env.example` con valores de placeholder. El secreto nunca va al repositorio.
8. **Autorización en cada endpoint de modificación.** Verificar que `req.user.negocioId === params.id` antes de actualizar datos de un negocio.
9. **Mobile-first en todo el frontend web.** Diseñar para 375px primero, escalar hacia arriba.
10. **Commits convencionales obligatorios.** `feat:`, `fix:`, `test:`, `refactor:`, `docs:`. Sin mensajes tipo "fix things" o "update".
